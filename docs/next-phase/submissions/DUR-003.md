## 2. Repairs

### B1 — state-chain reconciliation across abandoned intents

`reconcileGoalOperations` in `lib/goal-recovery.mjs` no longer stops at the
first undispatched intent. It builds a dynamic-programming map of reachable
before/after image states:

- The initial state is the first operation's before image.
- Every genuinely **dispatched** operation may extend a chain whose current
  image equals that operation's before image.
- Undispatched intents are skipped, not treated as barriers.
- The selected chain is the longest dispatched chain whose image matches the
  current disk bytes and mode; shorter branches and undispatched gaps remain
  attributable only when a continuous dispatched chain independently reaches
  the same observable state.

Bytes matching an undispatched after-image still cannot claim provenance, but
that rule now yields only when **no** continuous dispatched chain reaches the
current state. A dispatched-but-unapplied branch therefore cannot hide a later
branch resumed from an earlier reachable image. Discontinuous dispatched
history (external bytes landing between attempts) remains `divergent` with no
exact undo, rather than claiming external bytes.

### B2 — final commit authority re-read

`applyEditOperation` in `lib/goal-operations.mjs` re-inspects the goal after the
final target read and again immediately before publication:

- `assertCurrentCommitAuthority` compares the current goal generation, sequence
  and journal tail against the snapshot taken before staging, then revalidates
  `assertOperationAuthority` with a runtime timestamp, held-lock owner and the
  current lease.
- `beforeCapture` brackets the final target read with two fresh authority
  checks; `beforePublish` repeats the check after the displaced target has been
  verified.
- A committed cancellation, lease renewal, generation advance or sequence
  change during the final read is refused as `stale fence`; staged bytes are
  removed and the target remains byte- and mode-identical.

Lease renewal, cancellation during the final target read, cancellation during
displaced-target verification, and generation advance during the final read are
covered for both edit and delete.

### B3 — quarantine, verify, no-clobber publish, rollback and retention

`lib/pinned-write.mjs` now exposes `commitPinnedVerified`,
`writePinnedVerified` and `deletePinnedVerified`; `writePinnedAtomic` is
preserved unchanged for existing callers.

Publication protocol:

1. Stage new bytes in a private `.matrix-integration-*.tmp` file with the exact
   target mode.
2. Re-read commit authority and the live target (`beforeCapture`), then rename
   the live target to a private
   `.matrix-commit-<stem>-<hex>.displaced` quarantine name in the same directory.
3. Verify the **actual displaced object** (`verifyDisplaced`): bytes and mode
   must equal the approved before image. For undo, the displaced object must
   equal the undo target image.
4. Re-read commit authority and parent identity, and require the target path to
   be absent (`beforePublish`).
5. Publish with no-clobber `link(2)` (or unlink the verified quarantine for a
   deletion). `link(2)` cannot replace a newer concurrent target.
6. On verification refusal or a non-conflict publication failure, restore the
   exact displaced object with no-clobber `link(2)`. If a further concurrent
   replacement occupies the target, retain the quarantine, leave the external
   object untouched, and name the retained path in the error.
7. Creation uses `createOnly` with no-clobber `link(2)`; staging is cleaned on
   refusal. Cleanup failures after a successful publication are returned in
   `retained` paths (a retained quarantine contains the verified old bytes; a
   retained staging path contains the published bytes).

`applyEditOperation` and `applyExactUndo` both use this protocol, including
mode-only drift, creation races, deletion races, and undo of creations and
deletions. The protocol does **not** claim that a goal-store fence read and a
filesystem publication are one atomic operation; it verifies the actual object
removed from the target path and documents the residual boundaries below.

## 5. Residual boundaries and unresolved blockers

These are stated explicitly rather than claimed as solved:

- The filesystem cannot combine the final goal-fence read and publication into
  one atomic operation. A fence change committed after the last
  `beforePublish` authority re-read but before `link(2)`/unlink is still a
  residual window. The B2 requirement (recheck after the final target read) is
  satisfied; no claim of full store/filesystem atomicity is made.
- A crash after quarantine retains the displaced object under
  `.matrix-commit-*.displaced`. A crash after publication can leave both the new
  target and the quarantined old target; exact undo from durable recovery blobs
  remains available when the target was published, but automatic pruning of
  retained quarantine files is not implemented and may require operator
  recovery. A crash after quarantine before publication on a write intent is
  reconciled as `missing/missing-expected` and needs attention; the old bytes
  remain in the retained quarantine.
- Physical OS power loss, filesystem torn-page recovery and non-Linux
  platforms are NOT EVALUATED.
- Controller/executor and production-writer integration remain DUR-004/DUR-005.
- Independent re-review and acceptance were **pending** when this section was
  written; the independent acceptance review recorded **ACCEPTED** for this candidate
  on 2026-11-06. No acceptance entry was added to `docs/next-phase/AUDIT.md`; the
  verdict is recorded in the review, this submission and `STATUS.md`.
