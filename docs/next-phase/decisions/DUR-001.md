## Executable goal contracts

The contract implementation owns `lib/goal-contracts.mjs` and
`test/goal-contracts.test.mjs`, alongside this record and the lock spike. The
module is included in checkJs and has coverage floors of 90% lines, 75% branches,
and 100% functions. It validates metadata before returning an independent copy.
Its exported APIs cover IDs, normalized Linux paths, the goal record, lifecycle
changes, criterion evidence, reservation accounting, and stopped-goal amendments.

Goal, attempt, operation and criterion identifiers have distinct prefixes and UUIDv4
values encoded as 32 hexadecimal characters. Metadata schema version is 1. Root identity uses decimal device and
inode strings to avoid JSON integer precision loss. Manifest, target configuration,
test-plan and artifact bindings use SHA-256. The goal record accepts no arbitrary
provider, authority or credential fields. Criteria are exact test-plan hashes,
artifact path/content hashes, or human review descriptions, each with an ID and
revision. The goal record records operation IDs; the separate journal, intent,
receipt and lease contract layer is specified in the continuation below. The store is
not approved until that layer and the ownership policy pass review.

Each lifecycle mutation compares the goal ID, generation and sequence with the
caller fence. Successful mutations advance the sequence. Starting from ready or
entering reconciliation advances the generation and makes prior callbacks stale.
The store must persist that change under its lease before dispatch. Completion is
allowed only from running, with one accepted evidence record per criterion, matching
the current generation, manifest, criterion revision and plan/artifact hash. The
executor must establish evidence acceptance and current filesystem identity before
calling this pure function. Human decisions are supplied by trusted control code.

| Component     | Owns                                            | Proposed interaction with the contract layer                                                                              |
| ------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Store         | Journal, blobs, checkpoints and writer lease    | Validate records and compare the fence while locked, persist and sync before returning success                            |
| Reconciler    | Interpretation of incomplete effects            | Read intent and observed bytes, retain ambiguities, request fresh authority before undispatched work                      |
| Executor      | Attempt lifetime and cumulative accounting      | Reserve before dispatch, consume from a known reservation, retain uncertain reservations, invalidate evidence after edits |
| Policy bridge | Current-generation authorization                | Bind exact bytes/plan to the operation and generation, expire decisions after restart, check cancellation before dispatch |
| UI adapter    | Bounded projections and explicit user decisions | Render committed state, submit decisions through the verified control channel                                             |

All validators throw before returning on invalid input. All transforms return
copies and leave their inputs unchanged. I/O errors remain store/executor errors.
Cancellation stops new dispatch first, cancels owned processes, reconciles in-flight
effects, then persists a terminal attempt record. The lease remains held until the
teardown/reconciliation boundary is known. A clean run result alone maps to
needs-attention because criteria can remain incomplete. Aborts map to interrupted
and budget exhaustion maps to budget-exhausted using `lib/outcome.mjs` classification.

Initial per-goal budgets are 8 rounds, 24 tool dispatches, 32 provider requests and
600,000 active milliseconds. Proposed maxima are 128 rounds, 512 tools, 512 provider
requests and 86,400,000 active milliseconds. These are contract choices for review.
Every dimension includes used and reserved totals. Consumption transfers a known
amount from reserved to used, preserving the total. Interrupted/uncertain work
keeps its reservation. There is currently no reservation refund API. An explicit
budget increase is accepted only while budget-exhausted and cannot reduce another
dimension or reset counters. Timing reservations and crash persistence belong to
the executor/store. A monetary ceiling is outside this first contract.

Proposed CLI grammar remains the six goal commands in ARCHITECTURE.md. `start`
requires an objective and criteria file. `resume` requires a stopped goal and fresh
invocation authority. `list` and `inspect` are read-only. `pause` and `cancel` use
the verified owner channel. Suggested exits are 0 for completed work or a successful
read/control command, 1 for incomplete/failed work, 2 for invalid input, and 130 for
interruption. These remain proposals until CLI implementation and review. Ordinary
chat session resume and edit/test approval meanings continue to use their existing

## Observation

On Linux with Node 24.21.0 and the host `flock` utility, run:

```sh

```

The test starts a Node process through `flock --no-fork`, waits for an explicit
ready signal, and observes that a second `flock -n` process is denied without
running its command. After SIGKILL and observation of the first process's exit,
a second process acquires the same lock. The observed result was 1 pass, 0 fail,
0 skipped. This demonstrates contention and kernel release for that process only.

## Detached worker after lock owner death

The new cases wait for the detached worker to signal readiness, confirm a contender
is refused, and send SIGKILL to the lock owner. They test contention again before
allowing the surviving worker to write a sentinel in the temporary workspace.

| Descriptor handling                   | Second writer after owner death | Surviving worker                                | After worker exits |
| ------------------------------------- | ------------------------------- | ----------------------------------------------- | ------------------ |
| Default Node child descriptors        | Acquired the lock and executed  | Wrote the sentinel afterward                    | Lock available     |
| Explicit lock descriptor forwarding   | Refused with no command output  | Wrote the sentinel while still holding the lock | Lock available     |
| Forwarded descriptor closed by worker | Acquired the lock and executed  | Wrote the sentinel afterward                    | Lock available     |

The default descriptor case rules out treating
lock-owner exit as evidence that the workspace has stopped changing. Explicit
forwarding only keeps the lease while some process retains the descriptor. Closing
the forwarded descriptor before the owner is killed reproduces the race.

## Separate holder in the sandbox

The next spike uses the existing Bubblewrap snapshot mount layout and passes the
supervisor's flock descriptor via `--sync-fd` to the sandbox reaper. The command
checks that it has no descriptor for the lock, then starts a detached worker.
After SIGKILL of the supervisor and command, the worker confirms the command is
gone from the sandbox procfs. A second writer is refused while the worker waits.
Once released, the worker writes to the snapshot, exits, and the contender acquires
the lock. The live workspace has no sentinel. The experiment removes
`--die-with-parent` to exercise the surviving reaper path.

`node --test test/goal-lock-spike.test.mjs` passed 5/5 with no skips on Node 24.21.0
and Node 22.23.1 using Bubblewrap 0.13.1. This supports keeping the lock descriptor
with trusted supervisors and reapers and exposing only disposable snapshots to
detachable work. The Bubblewrap monitor can return the command's exit status before
its reaper has finished waiting for descendants. A production design must distinguish
those events, bound and reclaim lingering processes, and hold authority through any
live publication. See the [Bubblewrap process implementation](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c).

## Reaper death and guarded cancellation

The `work/dur001/reaper-cancel.py` harness in the Codex workspace exercised the
same snapshot mount layout with a detached worker writing a periodic snapshot
sentinel. The command dies first, and the Bubblewrap monitor exits 137 while the
worker continues. The harness uses Bubblewrap's setup announcement, verifies
namespace PID 1 and parent/child identity, then pins the reaper and worker with
Linux pidfds. A contender starts polling the lock before SIGKILL is sent through
the reaper's pidfd.

| Last lock holder at cancellation                                    | Node 24.21.0                                       | Node 22.23.1                                       |
| ------------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------- |
| Reaper alone                                                        | 5/5 acquisitions before either pidfd reported exit | 5/5 acquisitions before either pidfd reported exit |
| Separate guardian waits for worker and reaper exit before releasing | 5/5 acquisitions after both exits                  | 5/5 acquisitions after both exits                  |

All runs observed the worker stop and the live workspace remain untouched. The
test intentionally kills an active namespace. It makes no assumption that the
worker will finish within a cancellation budget, and the fixture has an emergency
exit timer for cleanup if the harness fails.

**Proposed direction:** keep the lease with a trusted guardian through cancellation
and live publication. Pass the descriptor to Bubblewrap's reaper as a secondary
holder, but treat reaper lock release as insufficient evidence of teardown.
Pin the running namespace before acknowledging dispatch. Cancellation signals
that exact namespace and confirms teardown while the guardian still owns the
lease. Only the trusted writer can publish to the live workspace, after validating
the generation and workspace identity. Any surviving job may write only to its
disposable snapshot. This proof covers cancellation with a surviving guardian.
Restart after guardian death still requires a recovery protocol and separate tests.

## Fresh-process recovery after guardian death

This is a design experiment, not production locking. It adds three cases to
`test/goal-lock-spike.test.mjs` and changes no production module, host setting or Git
history. The guardian deliberately does not forward its flock descriptor to Bubblewrap
and removes `--die-with-parent`, so the old namespace can survive guardian death while
the kernel lock is already free. That is the unsafe gap the recovery protocol must
close.

### Persisted evidence and recovery rule

The guardian writes `run.json` atomically before dispatch and adds identity only after
verification. It records schema version, goal/run IDs, boot ID, canonical workspace
path plus device/inode, lock path, lifecycle phase, guardian PID/start time, and, when
verified, Bubblewrap monitor and namespace-init PID/start time, PID-namespace inode,
detached-worker PID/start time, and the pending operation ID/path/before/after hashes.
The running fixture persists the edit intent, publishes the after bytes to the live
workspace, and is killed before a receipt exists.

Recovery is a separate `flock -n --no-fork` process given only the evidence directory;
it inherits no descriptor from the guardian. It holds the workspace lock while it:

1. validates boot, canonical workspace path and root device/inode;
2. requires phase `running`, the sandbox identity and the worker identity to be present;
3. re-reads each PID and requires the persisted start time, the recorded PID namespace
   inode, and namespace PID 1 for the sandbox init;
4. hashes the pending workspace file against the before/after images;
5. reopens the exact PID with a test-only Python `pidfd`, rechecks its start time and
   sends `SIGKILL` through that pidfd;
6. waits until the exact sandbox-init, monitor and worker identities are gone, rechecks
   the pending bytes and file inode/mtime/ctime, then publishes `ready`.

A test-only `continue-investigation` file holds recovery between lock acquisition and
identity checks so the competing-writer timing is deterministic; it is not crash
evidence. Writer fixtures acquire the same lock but execute only when both the run
phase and recovery state are `ready`. Otherwise they write a refusal record, exit 3 and
run no command. Thus an acquired flock is recorded but is not treated as proof that the
old run stopped.

The three cases beyond the earlier lock/reaper evidence observed:

- **Guardian death before sandbox identity was verified.** Evidence stayed at phase
  `starting` with `sandbox: null`; the old Bubblewrap process group remained alive. A
  writer acquired the free lock but refused because the phase was not ready and wrote
  no sentinel. While recovery held the lock the second writer was denied with no
  refusal record or execution. Recovery returned `needs-attention` with reason
  `sandbox identity was not verified before guardian exit`, `signals: []`, and did not
  signal the old sandbox. After the lock was released another writer acquired it, still
  refused, and left the live workspace at the before bytes. This is fail-closed, but
  the unverified old sandbox is left for cleanup rather than guessed at.
- **Guardian death after the detached worker started.** The old namespace and worker
  stayed alive after the guardian was SIGKILLed. A writer acquired the released lock
  and refused while the worker was still writing its snapshot heartbeat. During
  recovery another writer was denied by the lock, while the exact old identities
  remained present. Recovery verified boot/workspace/process identities, classified the
  pending write as `observed-applied`, SIGKILLed the exact namespace through pidfd,
  confirmed init/monitor/worker teardown, and left the live result bytes and file
  inode/mtime/ctime unchanged. Only then did it publish `ready`. The next writer
  acquired the lock and actually executed, writing its sentinel, while the reconciled
  result stayed at the after bytes. The old worker only ever wrote inside the
  disposable snapshot.
- **Mismatched process identity.** Evidence reused the PID of a live unrelated witness
  with a deliberately wrong start time. Recovery refused with
  `sandbox monitor identity mismatch` and `signals: []`; the witness stayed alive and
  its heartbeat kept advancing. Writers before and after the refusal acquired the free
  lock but refused, wrote no sentinel, and left the live workspace unchanged.

The experiment supports the direction that recovery must hold the workspace lock across
identity verification, containment/teardown and pending-effect reconciliation, and that
readiness must be persisted only after those checks. It also confirms that flock
acquisition alone is not evidence of an exclusive live writer.

### Method: deterministic barriers and SIGKILL as crash evidence

A child process is launched under `flock -n --no-fork`. It writes one durable
record, publishes a barrier marker, then blocks polling a gate file whose very
next action is the second durable write (or the live-file change). The test waits
for the marker and sends **SIGKILL**. SIGKILL is treated as process-crash
evidence: it runs no cleanup handler and performs no final flush, so the
persisted bytes at the barrier are exactly the bytes a fresh process would find
after a crash. This models a process crash only; it makes **no** power-loss or
filesystem-reordering claim, consistent with ARCHITECTURE.md section 4
("Document process-crash guarantees separately from power-loss/filesystem
guarantees"). `writeJsonAtomic` is a temp-file-plus-rename; the directory-sync
and `fsync` durability of a production store is out of scope here. The fresh
contender runs in a separate process with only the evidence directory (and the
same workspace lock), reads the persisted records itself, and records its
decision plus whether it executed a sentinel write in the workspace.

### Part A — crash between "ready" and publishing writer state

The current recovery publishes readiness with **two separate atomic renames**:
`run.json` (`phase:"ready"`) then `recovery.json` (`status:"ready"`), with no
generation token binding them. The new fixture reproduces that ordering
(`PUBLISH_SOURCE`), and a `naive-two-record` contender reproduces the current
policy (both records say ready, no generation fence).

1. **Disagreeing records (A1).** `writeInvestigating` publishes
   `recovery.json`=`investigating` first. Recovery is SIGKILLed at the barrier
   after writing `run.json`=`ready(gen1)` but before publishing writer state. A
   fresh process sees `run.phase="ready"` and `recovery.status="investigating"`
   — records that disagree. Both the naive two-record contender and a
   single-checkpoint contender refuse; no sentinel is written; the original
   bytes are unchanged. An acquired lock is again not proof of readiness.
2. **Reproduced defect (A2).** Generation 1 publishes both records completely.
   A generation-2 recovery is then SIGKILLed after publishing
   `run.json`=`ready(gen2)` but before republishing writer state, so the old
   gen1 `recovery.json`=`ready` survives. Persisted evidence is torn across
   generations (`run.generation=2`, `recovery.generation=1`). The current,
   unfenced `naive-two-record` policy **executes** — a contender writes after a
   partial/old-generation update. This is the failure reproduced first, before
   any fix is demonstrated, so the fix is shown to be necessary.
3. **Fix: single atomic checkpoint (A3).** `RECONCILE_SOURCE` publishes one
   generation/runId-fenced `checkpoint.json` with a single rename. A recovery
   SIGKILLed _before_ the checkpoint write leaves **no** half-ready state and
   the contender refuses. A valid completed checkpoint admits (positive
   control). An old-generation checkpoint, a `needs-attention` checkpoint and a
   truncated/corrupt checkpoint all refuse. Nothing is inferred from corrupt
   data; no write is executed.
4. **Fix: safe ordering + fence (A4).** Keeping two records, the demonstrated
   safe ordering is that a new generation's _first_ durable action invalidates
   writer state (`recovery.json`=`investigating@gen2`), and the contender fences
   on generation, runId and `complete`. The torn A2 state, the in-progress
   ordering state, and a wholly old-generation pair all refuse; a consistent,
   complete, current-generation pair admits. Both fixes close the A2 hole.

### Part B — edit intent persisted, live file not yet changed

`INTENT_SOURCE` persists an edit intent as its own record, with the **exact
private before/after images** and their SHA-256 hashes, then blocks on a barrier
whose next action is the live-file write. The writer is SIGKILLed at that
barrier, so the intent exists but the live file was never changed by the writer.
The test then arranges the observable bytes deliberately; recovery
(`RECONCILE_SOURCE`) classifies them against the exact intent hashes only —
never against a claim from the dead writer — and checks the **actual file bytes
and whether the contender executed**:

| Observable live image | Classification     | Contender | File bytes   | Recovery action                                          |
| --------------------- | ------------------ | --------- | ------------ | -------------------------------------------------------- |
| exact **before** (B1) | `not-applied`      | executes  | exact before | never re-applies; no receipt fabricated                  |
| exact **after** (B2)  | `observed-applied` | executes  | exact after  | records after as observed; never rewrites it             |
| **unexpected** (B3)   | `unexpected`       | refuses   | preserved    | needs-attention; explicit hash-bound resolution required |

For B2 the checkpoint records honest provenance ("observed bytes vs intent
hashes; Matrix authorship not claimed"), matching ARCHITECTURE.md section 6
("Matching after bytes proves observable state, not that Matrix caused every
external change"). For B3 the unexpected bytes are preserved with **no overwrite
and no rollback**; a `needs-attention.json` record is written; the contender
refuses. Progress requires an explicit `resolution.json` bound to the exact
observed hash, generation and runId: a wrong-hash resolution is still refused,
and only a matching resolution admits — still leaving the file bytes untouched.
The file is never written by recovery in any branch (`reconcile.wroteResult` is
false throughout).

Each of the seven cases uses a fresh temporary workspace, evidence directory and

process group (`detached: true`) with a 15-second emergency exit; teardown kills
the process group (`process.kill(-pid, "SIGKILL")`), waits briefly, and removes

New **unresolved risks** introduced or left open by this continuation:

- The single atomic checkpoint and the generation fence are test-fixture
  demonstrations of a _safe ordering_, not a production store. A real store must
  still add and verify `fsync` of file and parent directory, 0600/0700 modes,
  checksum-linked journal records, checkpoint caps, and the "keep a verifiable
  previous checkpoint" rule from ARCHITECTURE.md section 4. Atomic rename alone
  is not a durability claim; these tests exercise process crashes only, not
  power loss or filesystem reordering.
- The generation value is supplied by the fixture. A production design must
  define how generations are minted, persisted and monotonically advanced, how
  an executor proves it owns the current generation before each mutation, and
  how a stale executor's late callback is fenced (section 7). Reusing a
  generation, or a trusted-writer bypass of the fence, is not tested here.
- The contender policies are test-only. Ordinary interactive/headless runs,
  parallel publication and any writer that does not consult the fenced state can

### Journal record

Required fields are `schemaVersion`, `sequence`, `goalId`, `attemptId`, `generation`,
`kind`, `operationId`, `prevChecksum`, `payload` and `checksum`. `kind` is one of
`attempt`, `intent`, `dispatch`, `receipt`, `state`, `budget`, `evidence`, `terminal`.
The payload always carries `schemaVersion: 1`; operation payloads are additionally
validated by the typed intent/receipt contracts.

- `sequence` starts at 1 and advances by exactly one. A gap is refused, not repaired.
- `prevChecksum` is `null` only for sequence 1; otherwise it must equal the previous
  record's `checksum`. A broken link is refused before any payload is interpreted.
- `generation` is non-decreasing and advances by at most one per record. Generation 0
  requires `attemptId: null`; a positive generation requires an attempt ID. A record
  in the same generation must retain the same attempt ID; a new generation must use an
  attempt ID never seen in that chain.
- Each operation may have one prepared intent, then one dispatch, then one receipt.
  Duplicate intents, dispatch without intent, receipt without dispatch, duplicate
  receipts and more than 128 operations are refused. A dispatch must match its
  prepared intent in every field except `state`; a different plan or edit image under
  the same operation ID is refused.
- A receipt's own `sequence` must equal the journal sequence of its record, so a
  durable completion sequence cannot be copied from another attempt.
- Chain limits are 1,024 records and 32 MiB by default. The full goal record remains a
  checkpoint concern; journal payloads stay below 64 KiB each.

Checksums detect accidental damage. They do not authenticate against a malicious
same-UID process, and the contract does not claim otherwise.

### Operation intent and authority binding

Required fields are `schemaVersion`, `goalId`, `attemptId`, `generation`,
`operationId`, `kind`, `arguments`, `planHash`, `authority`, `workspace`,
`preconditions`, `edit`, `reservation` and `state`. `kind` is `read`, `search`,
`edit`, `test`, `command` or `provider`.

- `arguments` is `{sha256, blob}`. Raw scripts and normalized argument bodies stay in
  private blobs; `blob` may be `null` only when the caller can re-derive the exact
  arguments. The digest is always required.
- `authority` is `{kind, planHash, decisionId, scope}` with `scope: "operation"`.
  `decisionId` is a non-executable audit reference matching `decision_<32hex>`.
  Edit, test and command intents must use matching authority kinds and bind
  `authority.planHash` to the intent plan hash. Read, search and provider intents use
  `kind: "none"` with both plan and decision fields `null`.
- `workspace` repeats the canonical absolute path, decimal device and inode, Git
  revision (`null` outside Git) and approved manifest digest. A mismatch against the
  persisted goal is refused.
- `preconditions.files` is bounded to 8 entries of `{path, exists, sha256}`. An edit
  must carry exactly one precondition that matches its before image.
- `edit` is `{path, before, after}` or `null`. Each image is
  `{exists, sha256, mode, blob}`; absent images carry `null` hashes and no blob. The
  blob digest identifies the exact private recovery image. A no-op edit is refused.
- `reservation` uses the existing budget counter shape and is validated as non-negative
  usage. The executor reserves it through `reserveOperationBudget` before dispatch.
- `state` is `prepared`, `dispatched` or `observed`. Dispatch is allowed only from
  `prepared`; observation only from `dispatched`. The journal records the same state.

### Operation receipt

Required fields are `schemaVersion`, `goalId`, `attemptId`, `generation`,
`operationId`, `sequence`, `status`, `evidence`, `files`, `process`, `usage` and
`uncertainty`.

- `status` is `succeeded`, `failed`, `denied`, `cancelled`, `interrupted` or
  `uncertain`. An `uncertain` status requires a non-`none` uncertainty kind.
- `evidence` is at most 16 unique SHA-256 references to private artifacts.
- `files` is at most 128 unique paths, each with `matches-before`,
  `matches-after`, `absent` or `unexpected` and the observed hash. Unexpected bytes are
  preserved, consistent with the recovery table in ARCHITECTURE.md.
- `process` is `null` or `{exitCode, signal}` with a 0-255 exit code or a `SIG...`
  signal; at least one must be known.
- `usage` is the actual charge and must not exceed the intent reservation. Settlement
  consumes that amount through `updateGoalBudget`; unused reservation is not refunded.
- A successful edit receipt must record the exact after image (or `absent` for a
  deletion). Matching after bytes proves observable state, not Matrix authorship.

### Lease and generation ownership

Required fields are `schemaVersion`, `leaseId`, `goalId`, `attemptId`, `generation`,
`workspace`, `owner`, `acquiredAt` and `expiresAt`. The workspace binding is only the
canonical path, device and inode; the approved manifest remains in the goal record so
an edit does not falsely invalidate its own lease. The owner binding is
`{pid, startTime, bootId}` with a decimal kernel start time and a bounded boot ID.

`createGoalLease` refuses a goal that is not `running`, `awaiting-approval` or
`reconciling`, or has generation 0. It mints the lease ID in trusted code and takes
`now` and `ttlMs` from the caller; it never reads the clock or a model argument. The
lease window is at most 120,000 ms. `renewGoalLease` requires the exact owner and a
live window, then re-mints `acquiredAt`/`expiresAt`. An expired or rolled-back lease
is refused before the next effect.

A trusted runtime must use this protocol:

1. Acquire the reviewed workspace lock and read the last verified checkpoint and
   journal head. If the prior attempt ended without a terminal record, reconcile first;
   do not start a new effect from uncertain state.
2. Require a stopped/ready goal. Allocate `attemptId = newGoalId("attempt")` in trusted
   runtime code, never from a model or provider tool-call ID.
3. Advance the generation with `transitionGoal` (`ready -> running` or a stopped state
   `-> reconciling`) and persist the new goal checkpoint and attempt-start journal
   record before any dispatch. The persisted generation is the fence; a crash between
   the two writes is an interrupted attempt, not permission to reuse the generation.
4. Create the lease with `createGoalLease(goal, {attemptId, owner, now, ttlMs})` using
   the process identity verified from the OS (PID plus start time and boot ID), persist
   it with the fenced checkpoint, and never accept a caller-supplied lease.
5. Before every mutation, call
   `assertOperationAuthority(intent, {goal, lease, owner, now})`. It re-validates the
   goal, lease goal/generation/attempt/root/owner/expiry and the intent workspace,
   manifest and generation. Only then reserve budget, append and sync the intent
   record, and dispatch.
6. Renew with `renewGoalLease` before `expiresAt`. If renewal or lease validation
   fails, stop before the next effect and record an interrupted/uncertain attempt; do
   not continue on a stale lease.
7. After the effect, observe bytes, call `assertOperationReceipt`, append the receipt
   with its durable sequence, settle the reservation, and only then expose completion.
   Persist a checkpoint before showing a terminal result.
8. Route every late callback through `assertOperationFence` or
   `assertOperationAuthority` and include goal, attempt, generation and operation. A
   callback from an older attempt cannot approve a write, consume budget or overwrite
   the current result. Do not add a trusted-writer bypass around this check.

The module validates records; the store still owns `fsync`, parent-directory sync,
0600 files, 0700 directories and atomic checkpoint publication. Those are not claimed
by this contract layer.

### 1. Two-process Linux lock tests: Symlink aliasing, extended root replacement, and live writer participation

Five focused tests in `test/goal-lock-spike.test.mjs` establish Linux process and filesystem boundaries (bringing the spike suite to 20 tests, all passing on Node 24.21.0 and Node 22.23.1):

- **Symlink aliasing (`DUR-001 symlink aliasing: canonical workspace root prevents alias from acquiring a separate lock`):**

### 2. Selected Linux process ownership mechanism

- **Single Chosen Production Mechanism:**
  Matrix decisively selects a **dedicated in-tree static C helper binary (`bin/matrix-pidfd-helper`)**.
  - _Rationale over N-API Addon:_ Matrix is an ESM Node.js application designed with zero native npm compilation dependencies (no `node-gyp`, no Python or C++ headers required during `npm install`). An N-API addon creates ABI compatibility friction across Node 22 and 24 and couples runtime installation to local development toolchains. A standalone static C helper binary compiled with standard glibc/musl syscall interfaces (`syscall(__NR_pidfd_open, ...)`, `syscall(__NR_pidfd_send_signal, ...)`, `poll(2)`) is self-contained, architecture-portable across Linux distributions, auditable, and eliminates all Node addon ABI maintenance.
  - _Execution Boundary:_ Invoked by the supervisor via `spawnSync`/`spawn` with explicit arguments: e.g. `matrix-pidfd-helper verify-signal <pid> <expected_boot_id> <expected_start_time> <sig>` and `matrix-pidfd-helper wait <pidfd>`.

- **Process Identity Verification via procfs and Race-Free Pinning:**
  When a recovery process starts after guardian crash or interruption:
  1. _Host Boot Verification:_ Reads `/proc/sys/kernel/random/boot_id` and requires an exact string match with `checkpoint.bootId`. If the host rebooted, all prior PIDs are invalid; recovery marks the prior run `needs-attention` and refuses to signal any PID.
  2. _Workspace Identity:_ Verifies `fs.realpathSync(workspace)` matches `checkpoint.workspace` and `fs.statSync(workspace)` matches recorded decimal `dev` and `ino` strings.
  3. _procfs Identity Check:_ Reads `/proc/<pid>/stat` to extract process start time (field 22 / tick index 21), confirms command name in `/proc/<pid>/comm`, verifies PID namespace inode in `/proc/<pid>/ns/pid`, and confirms `NSpid: 1` in `/proc/<pid>/status` for the Bubblewrap sandbox init.
  4. _Race-Free Pinning via pidfd:_ Opens the target process using `syscall(__NR_pidfd_open, pid, 0)`. While holding the pinned pidfd, re-verifies `/proc/<pid>/stat` through the pinned descriptor (or inspects `/proc/self/fdinfo/<pidfd>`) to eliminate any PID-wrap or PID-reuse race between procfs inspection and fd allocation.

- **Signaling and Teardown Wait:**
  - Signals the pinned process using `syscall(__NR_pidfd_send_signal, pidfd, SIGKILL, NULL, 0)`.
  - Waits for process termination by polling `POLLIN` on the pidfd using `poll(2)` or `epoll_wait(2)`. Under Linux, a pidfd becomes readable with `POLLIN` if and only if the associated process has terminated, with exit status retrievable via `waitid(P_PIDFD, pidfd, ..., WEXITED)`.

- **Lock Retention Through Teardown:**
  - The trusted guardian supervisor exclusively holds the advisory lock descriptor (`flock -n --no-fork`) on `<canonicalWorkspace>.lock` with `O_CLOEXEC` set. The descriptor is never leaked or forwarded to untrusted commands or sandbox descendants.
  - The lock is NOT released when child processes die or when the sandbox reaper exits.
  - The supervisor maintains the lock across reaper/command exit, across detached worker death, and throughout namespace teardown until all pidfds report `POLLIN` (exit confirmed) and pending effects are reconciled.

- **Doctor Probes (`bin/matrix.mjs doctor` / `lib/doctor.mjs`):**
  Preflight checks probe four required Linux capabilities:
  1. _Kernel Version & Syscalls:_ Requires Linux kernel >= 5.3 (introducing `pidfd_open` [syscall 434] and `pidfd_send_signal` [syscall 424]). Probed via `matrix-pidfd-helper --probe` or direct probe execution.
  2. _procfs Availability:_ Verifies `/proc/sys/kernel/random/boot_id`, `/proc/self/stat`, `/proc/self/status`, and `/proc/self/ns/pid` are mounted, readable, and non-empty.
  3. _Bubblewrap Isolation:_ Probes `bwrap` binary availability and verifies unprivileged user and PID namespaces are functional.
  4. _Lock Semantics:_ Verifies non-blocking `flock` (`flock -n`) semantics on the target workspace filesystem, rejecting remote/network mounts (NFS, CIFS, 9P) where lock semantics are broken or advisory-only.

- **Fail-Closed Refusal on Missing Capabilities:**
  If any Doctor probe fails, Matrix refuses to start or recover a durable goal:
  - Error: `E_CAPABILITY_MISSING: Linux pidfd and procfs support required for durable goal execution`.
  - Exit code: 2 (unsupported environment / invalid invocation).
  - Effect: Zero lock files created, zero leases written, zero subprocesses spawned, and zero bytes modified in the live workspace.

### Model-agent write lock lifetime repair

The prior `assertWorkspaceWritable` probe exited before the atomic write. A competing
process could take the lock between the successful check and the rename. The live

## 2026-11-11 review addendum: open contract discrepancy

**Status: repair SUBMITTED for independent security review. The contract above is
unchanged, and it is not treated as met until that review accepts it.**

The durable-snapshot contract recorded in this decision record states that detachable
work is "exposing only disposable snapshots" and that "any surviving job may write only
to its disposable snapshot". The shipped durable-goal test path does not meet that
contract, and the contract text above is deliberately left unchanged.

What the implementation does. `lib/goal-containment.mjs` starts the goal's approved
test command with:

```
bwrap --unshare-user --unshare-pid --dev-bind / / -- node lib/goal-guardian.mjs
```

and `lib/goal-policy.mjs` sets that command's working directory to the live workspace
(`plan.cwd ?? realpathSync(workspaceRoot)`). The namespace therefore exposes the live
host filesystem read-write and the host network, and the command's working directory is
the live workspace. The existing `run_sandboxed_command` boundary in
`lib/linux-bwrap.mjs` does the opposite: a disposable no-follow snapshot, a read-only
minimal root, a new empty network namespace and a cleared environment.

Reproduction on the review host, using that exact argv: a process inside the namespace
created a file on the live host filesystem and reached the host loopback network.

Why it is recorded rather than closed. The discrepancy is not a documentation defect.
The implementation provides process-ownership containment — PID namespace, pinned
namespace identity, guardian, reviewed pidfd signalling, durable teardown proof — but
it does not provide the disposable-snapshot or network isolation that this record
requires. Documenting the implementation does not meet the contract, and the contract
must not be treated as met by documentation alone.

Scope of the exposure. Only a test command that a user has explicitly trusted and
approved can reach this boundary: the ordinary repository and test-plan trust gate, an
explicit approval of the exact plan and a separate `--allow-tests` decision are all
required, and `--yes` authorizes edits only. The ordinary, non-goal test path already
runs repository test code on the host with the host user's permissions, so the goal
path adds process-teardown guarantees without introducing a new class of host
execution. The durable evidence model binds test evidence to a dispatch-time
fingerprint, so a test that changes a declared artifact cannot produce a pass
(QA-101 CR-09). The shipped `README.md` and `MATRIX.md` now state the boundary, the
credential exposure and the required trust explicitly, so no user-facing claim is
inaccurate.

Acceptable dispositions, for the chief to choose:

1. **Meet the contract.** Give the goal test path the same disposable, no-network
   snapshot boundary as `run_sandboxed_command`, keeping the live-workspace criteria
   semantics by evaluating criteria against the snapshot and reconciling it under the
   existing store fencing.
2. **Amend the contract by review.** Amend this record, through a fresh independent
   review, with an explicit statement of the accepted live-filesystem and host-network
   boundary, its credential exposure, and the trust decision that authorises it.

   looked at modes.
2. **A working-directory selection is not a coverage proof.** A plan whose
   working directory was `workspace/tests` read `../input.json`. The identity
   covered the selection directory, the named configuration, the selected files
   and the static import closure, so changing that sibling file left the
   identity unchanged and the goal completed on stale evidence.

workspace is the selection root; the snapshot's own exclusion rules and
entry/directory/depth/byte budgets are imported from `lib/linux-snapshot.mjs`
rather than duplicated; the traversal is bounded and never follows a symbolic
link; and every entry records its existence, entry type, permission bits,
content digest and symbolic-link target. The plan's files, the runner
configuration, its working directory and the goal's artifact and edit paths
remain named inputs as well. A working-directory selection or a static import
closure cannot establish complete coverage for arbitrary approved test code and
is no longer treated as one. The same identity is applied at dispatch, at the
live-versus-snapshot comparison before any repository code runs, after the test
returns, at acceptance and on resume. An input that cannot be read or hashed, a
