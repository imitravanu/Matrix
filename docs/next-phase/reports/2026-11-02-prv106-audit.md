## 5. Mechanism isolation matrix results

One family per run. Expected versus observed per cell; loot per cell.

### 5.1 Family 1 - candidate binding and serialization

- **C1a** post-apply unauthorized rewrite (marker append by a second approved
  proposal). Expected: `checks.edit` fails while agent verification of agent-sent
  bytes passes, `taskSuccess: false`. Observed exactly that: `checks.edit: fail`,
  verification `pass`, and the authoritative run ran against the marker-containing
  bytes, so the byte binding holds at score time (`loot-e2e-c1a.json`).
- **C1b (alternate member of the repaired family)** Unicode BOM prepend via a
  single proposal. Expected and observed: `checks.edit: fail`, verification
  `pass`, `taskSuccess: false` (`loot-e2e-c1b.json`).
- **C1c x2** the last binding wins, both directions. Expected: first-broken bytes
  overwritten by a correct proposal end with `edit: pass` and a verification pass
  against the final bytes, so `taskSuccess: true`; correct-then-broken ends with
  `edit: fail` plus a verification fail on the broken bytes. Observed exactly
  (`loot-e2e-c1c-broken-then-correct.json`, `loot-e2e-c1c-correct-then-broken.json`).
  This is the direct proof that the score-time read binds to the final on-disk
  bytes, and that `checks.edit` includes the verification coupling (finding F-3).
- **Laundry unit cells** (`f1-unit.log`, 11 cells, no disk residue): line-number
  coercion (NaN, oversize, valueOf-throwing/min-zero objects), container-element
  smuggling (proxy and array), type confusion, and TAP-shaped proposal strings
  inside the proposal - all honest `fail` outcomes; `propose_edit` semantics held
  (`start_line` inclusive, `end_line` exclusive per `lib/model-agent.mjs:170`) and
  seeded-identical proposals were rejected as no-ops.
- **VM-inertness unit cells** (same log): import-free payloads that attempt marker
  files on the host, `Object.defineProperty` on the invoker binding,
  `Object.assign`, `delete` - the binding stays non-writable and
  non-configurable, no host-visible residue, error classes honest.
- **Binding discovery** `getOwnPropertyNames` on the agent context reveals the
  invoker's binding name, and a direct call of the discovered invoker is
  equivalent to a redefine attempt. Replacement is blocked; the name disclosure is
  recorded as finding F-4. The validation token is not inferable from the
  candidate context (token-free `jsonl` audit log confirmed by grep).

### 5.2 Family 2 - stdin authority and fixture integrity

- **C2d (alternate member)** a decoy `authoritative-*` directory containing a

  the real workspace bytes on stdin and ignores decoys; no FIFO hang. Observed:

### 5.3 Family 3 - receipt and exit integrity

- **C3c (alternate member)** forgery against a **real** scoring child of a live
  `runProviderEvaluation` run, with pid eligibility proven by exact scoring argv
  plus a ppid chain into the audit's own child (direct spawn or exactly one
  bubblewrap hop). Observed on an eligible same-uid host spawn: the real receipt
  token was disclosed (recorded only as a sha256, `c90a9d82...baad`), the forged
  passing TAP block carrying that token was accepted, and the substituted
  `exit_group(0)` was recorded by the scorer as a passing run
  (`loot-e2e-f3.json`, `loot-e2e-f3-eval.json`).
- **Ceiling of the forgery family**: the forged receipt makes
  `authoritativeVerification.ok`/`behavioralVerification.ok` true for wrong bytes,
  but `checks.edit` still fails on byte binding for wrong bytes, so `taskSuccess`
  stays `false` and `report.ok` stays `false`. Forgery alone cannot launder a
  wrong source end-to-end; the agent-side gate is the ceiling. Result-phase
  children are plain same-uid host spawns (`eval/provider-eval.mjs:600-604`),
  while the agent's own verify path runs under the bubblewrap snapshot runner
  (`:560-582`). See the boundary observation in section 7.
- **Injection flip attempt (C3 post-tail)** injecting a `# pass 1` / `# fail 0`
  tail after the honest summary into a child's output. Expected: gates must not
  flip. Observed: gates did not flip - the parser anchors the `#`-formed counts to
  the first match (`lib/process.mjs:670-671`) and the gate conjunction requires
  `failed === 0 && passed > 0 && completed` (`eval/provider-eval.mjs:355-362`).
- **Honest refusal** a second scoring child, scanned before its stdin phase, had
  no token material in memory; the forgery tool refused eligibility
  (`compose-failed`), so eligibility proof does not over-match.
- **Unverified variant** the same injection using the info-symbol-formed pass/fail
  lines instead of `#`-formed ones was not demonstrated (section 9).

### 5.4 Family 4 - detached-process interference

- **C4b (alternate member)** discovery race: leak scans driven from explicit-pid

  `snapshot file exceeds its byte budget` (`loot-e2e-huge40.json`,
  `loot-e2e-huge40-snapshot.json`). Three stacked ceilings are documented:
  SSE 1,048,576 bytes per event, then 32KiB per tool argument, then the snapshot

### 5.5 Family 5 - report and acceptance semantics

- **C6a x2** provider-side count lies. Expected: the provider's claims about the

## 7. Findings and repair directions

### Boundary observation (documented limitation, not a new P0/P1)

On this host, with `kernel.yama.ptrace_scope = 0`, a same-uid ptrace-attached
process can disclose the real receipt token from a plain host-spawned result-phase
child (`authoritative`/`behavioral`, spawned without the runner at
`eval/provider-eval.mjs:600-604`) and forge a passing TAP plus a substituted
`exit_group(0)`. The README documents that scoring itself is not sandboxed, the
repair routes the agent's own verify path through the bubblewrap snapshot runner
(`:560-582`), and the agent-side gate keeps `taskSuccess`/`report.ok` false for
wrong bytes even under a forged receipt (section 5.3). This is recorded as a
residual of the documented boundary rather than a finding against the repaired
candidate; a repair wave that extends the runner path to the result-phase spawns,
or a hardened `ptrace_scope`, would close it. Direction, not implementation: make
result-phase verification spawn under the same snapshot runner as the agent path.

### P3 findings (advisory; each with location and repair direction)

- **F-1 - `checks.target` is a hardcoded pass and is excluded from
  `taskSuccess`.** `eval/provider-eval.mjs:651` sets
  `target: { status: "pass" }`, and `taskSuccess` (`:667-674`) never includes
  `checks.target`. The check is decorative for both acceptance paths.
  Direction: either bind `checks.target` to a real task/target assertion or drop
  it from the report; if kept meaningful, include it in the `taskSuccess`
  conjunction. Observed in the CTRL-1 and c1a loot as well.
- **F-2 - the behavioral gate reuses the authoritative fixture vectors, so an
  overfit proposal passes everything.** The planted fixture content is identical
  between the authoritative and behavioral runs, so a proposal that hard-codes
  the fixture vectors passes both gates and reaches `taskSuccess: true` without
  correct behavior (`loot-e2e-overfit.json`). Direction: derive the behavioral
  run's vectors from a different distribution or a transformed variant so the two
  gates demand distinct evidence; keep both import-free.
- **F-3 - `checks.edit` conflates byte binding with run verification.**
  `eval/provider-eval.mjs:657` requires `authoritativeOk` inside `checks.edit`,
  so the check is not a pure byte-binding check: a byte-correct source that
  fails verification reports `edit: fail` (seen in the c1c correct-then-broken
  cell). The composition is conservative (it cannot weaken the ceiling), but the
  two concerns are indistinguishable in the report. Direction: either split the
  pure byte-binding predicate from the verification coupling into separate
  fields or document the coupling in the report schema so consumers can read the
  difference.
- **F-4 - the invoker binding is discoverable by name in the agent context.**
  `getOwnPropertyNames` on the agent context reveals the invoker's binding name
  (`f1-unit.log`). Replacement and deletion are blocked (validation held), the
  direct call of the discovered invoker is not an advantage over the tool path,
  and the token is not inferable from the context - so this leaks structure, not
  privilege. Direction: pass the invoker (and any privileged reference) as an
  explicit argument into the evaluation context rather than installing it as a
  context global, so the agent cannot enumerate its binding.

### Laundering attempts that failed closed (recorded, no finding)

All mechanism attempts outside the above families failed closed: VM escape
attempts inert with no disk residue; decoy and FIFO fixtures ignored; provider
lies ignored; abort semantics honest; not-evaluated gating honest; payload ladder
denied in the right order; post-tail `#` injection did not flip gates; the
scored-bytes binding held in both overwrite orderings and under BOM corruption.
